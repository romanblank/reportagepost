# Восстановление VM с нуля

_Создано 2026-08-01 по находке аудита (P2, инфраструктура). Проверяйте и обновляйте при каждом изменении инфраструктуры._

## Зачем

`setup-server.sh` идемпотентно настраивает уже готовую машину: он предполагает установленные docker, nginx и certbot, существующего пользователя `rp`, привязанный сервисный аккаунт с доступом к Lockbox и настроенный DNS. Всё это знание жило только в истории переписки — то есть при смерти или компрометации VM восстановление превращалось бы в археологию на несколько часов, причём в момент, когда прод лежит, а прямого SSH у оператора нет (провайдер режет путь к Yandex Cloud — см. CLAUDE.md).

При этом **всё состояние платформы — вне VM**: база в Managed PostgreSQL, файлы в Object Storage, секреты в Lockbox, образы в GHCR. Машина одноразовая. Восстановление — это 15 минут по инструкции, а не расследование.

## Что нужно иметь под рукой

- доступ в консоль Yandex Cloud (или `yc` CLI, авторизованный на нужный каталог);
- права на DNS-зону `reportagepost.com`;
- доступ к настройкам репозитория на GitHub (секреты Actions).

## Шаг 1. Создать VM

```bash
yc compute instance create \
  --name reportagepost-app \
  --zone ru-central1-a \
  --platform standard-v3 \
  --cores 2 --memory 4 --core-fraction 100 \
  --create-boot-disk image-family=ubuntu-2404-lts,image-folder-id=standard-images,size=30,type=network-ssd \
  --network-interface subnet-name=default-ru-central1-a,nat-ip-version=ipv4 \
  --service-account-name reportagepost-vm \
  --metadata-from-file user-data=deploy/cloud-init.yaml \
  --ssh-key ~/.ssh/reportagepost_deploy.pub
```

Ключевое здесь — `--service-account-name`: именно привязанный к инстансу сервисный аккаунт даёт `fetch-secrets.sh` доступ к Lockbox через metadata-токен, без единого ключа на диске. У аккаунта должна быть роль `lockbox.payloadViewer` на секрет с конфигурацией платформы.

Если сервисного аккаунта нет (восстановление после потери всего каталога):

```bash
yc iam service-account create --name reportagepost-vm
yc lockbox secret add-access-binding --id <SECRET_ID> \
  --role lockbox.payloadViewer \
  --service-account-name reportagepost-vm
```

`SECRET_ID` захардкожен в `deploy/fetch-secrets.sh` — сверьте, что он совпадает с реальным секретом.

## Шаг 2. Направить домен

Обновить A-записи `reportagepost.com` и `www.reportagepost.com` на новый внешний IP. Проверить: `dig +short reportagepost.com`.

Пока DNS не переехал, certbot сертификат не выдаст — шаг 4 нужно делать после распространения записей.

## Шаг 3. Обновить секреты GitHub Actions

В настройках репозитория (Settings → Secrets and variables → Actions):

- `PROD_HOST` — новый IP;
- `PROD_SSH_KEY` — приватный ключ, чей публичный передан в `--ssh-key` (пользователь `rp`).

Остальные секреты (`TELEGRAM_BOT_TOKEN`, `JOBS_SECRET` и прочие) не привязаны к машине и менять их не нужно.

## Шаг 4. Выпустить сертификат и развернуть

1. Запустить workflow **SSL** (Actions → SSL → Run workflow) — он получает сертификат Let's Encrypt и настраивает автопродление.
2. Запустить **CI/CD** (или сделать пустой коммит в main) — он выполнит `setup-server.sh`, вытянет секреты, накатит миграции, засеет справочники и поднимет контейнер.
3. Проверить: `curl -s https://reportagepost.com/health` — версия должна совпасть с последним SHA в main.

Если что-то не сходится — смотреть `gh run view <id> --log-failed`. Прямого SSH с ноутбука оператора нет, вся диагностика через Actions.

## Шаг 5. Убедиться, что фоновые задачи ожили

`setup-server.sh` ставит их сам, но проверить стоит — они молчаливые:

- `/etc/cron.d/rp-maintenance` — пересчёт рейтингов и чистка служебных таблиц (02:30 UTC);
- `/etc/cron.d/rp-heartbeat` — сторож свежести бэкапов;
- watchdog контейнера.

Дополнительно запустить вручную workflow **Restore drill**: он развернёт последний дамп во временный контейнер и сверит количество строк с боевой базой. Это единственная проверка, доказывающая, что резервные копии пригодны, — и на новой машине её стоит прогнать сразу.

## Что НЕ нужно делать

- Не восстанавливать данные на VM: база и файлы живут вне её, машина не хранит ничего, кроме временных файлов и логов.
- Не копировать `.env.prod` со старой машины: он собирается из Lockbox при каждом деплое. Ручная копия немедленно устареет и разойдётся с источником правды.

## Проверка процедуры

Инструкция считается рабочей, только если по ней прошли целиком хотя бы раз. До первого учения (создание второй VM, разворот, проверка `/health`, удаление) считайте её проверенной наполовину — этот же урок уже был получен на бэкапах, которые «работали» пять ночей подряд, пока их не попробовали восстановить.
