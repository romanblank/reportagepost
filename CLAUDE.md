- **🔴 Грабля SIGPIPE в bash-проверках (2026-08-01, стоила ТРЁХ прогонов бэкапа)**: `zcat file | grep -q ...` под `set -o pipefail` = ложный провал. `grep -q` выходит после первого совпадения и закрывает канал → `zcat` падает с SIGPIPE (код **141**) → pipefail валит весь конвейер → `if ! ...` читает это как «не найдено». Проверка НАХОДИЛА таблицу и рапортовала обратное. На macOS НЕ воспроизводится (иначе обрабатывается сигнал) — локальная проверка regex ничего не покажет. ПРАВИЛО: в проверках архивов распаковывать один раз во временный файл и считать в переменную (`grep -c`, `awk` дочитывают вход), не обрывать чтение через `-q`/`head` внутри конвейера. Код 141 в логе = ищи ранний обрыв канала, а не отсутствие данных.

- **🔴 Расширения PostgreSQL в Managed-кластере ставятся НЕ миграцией (2026-08-02)**: `CREATE EXTENSION pg_trgm` в миграции упал на проде — `permission denied, must be superuser`. В Yandex Managed PostgreSQL расширения включаются через API кластера: `yc managed-postgresql database update <db> --cluster-id <id> --extensions pg_trgm` (флаг ЗАМЕНЯЕТ список — перечислять все нужные). После включения `CREATE EXTENSION IF NOT EXISTS` в миграции проходит без прав и остаётся нужен для локальной БД и CI. Хуже самого падения его последствие: Prisma помечает миграцию failed, и это блокирует ЛЮБЫЕ следующие (P3018) — лечится `npx prisma migrate resolve --rolled-back <name>` на проде, после чего миграция применяется начисто. Правило: любая миграция, требующая прав уровня кластера (расширения, роли, настройки), сначала проверяется на прод-подобной среде, а не на локальном docker-PG, где ты superuser.

- **Кэш каталога и адресная выборка (2026-08-03)**: страница города была единственной большой без кэша — до 13 запросов на КАЖДЫЙ заход, при том что для главной `unstable_cache` сделан давно. Кэшируется только неперсонализированное (счётчики жанров/техники, полка) с тегом `catalog:<city>`; список авторов остаётся живым. В `CATALOG_INCLUDE` теперь `select`, а не `include`: последний тянул оборудование, FAQ, шоурилы и языки на 24 карточки. Пул соединений задан явно (`max`, `statement_timeout`) — дефолт node-postgres 10 не покрывал даже одну страницу каталога.

- **Время в базе — `timestamptz` (2026-08-03)**: инвариант «UTC в базе» держался только на том, что и приложение, и сессия PostgreSQL всегда в UTC. Тип `timestamp` зоны НЕ хранит: psql с другим TimeZone, restore на сервер с иным GUC или реплика в другом регионе читали бы время со сдвигом молча. 65 колонок переведены; у колонок-ДАТ (`@db.Date`) зоны быть не должно — конфликт атрибутов ловит `prisma validate`.
- **Плановый пересчёт рейтингов идёт КУРСОРОМ (2026-08-03)**: прежняя версия читала все одобренные анкеты со всеми фотографиями одним запросом — на тысячах авторов это сотни мегабайт в контейнере и риск не уложиться в `maxDuration`, причём молча: недосчитанный рейтинг ничем себя не выдаёт.

- **WebP только при подтверждённом наличии файла (2026-08-03)**: браузер НЕ откатывается на `<img>`, если файл из `<source>` вернул 404 — картинка просто битая. Поэтому `Photo.hasWebp`, а не «попробуем и посмотрим»: `<source type="image/webp">` рендерится ТОЛЬКО при флаге. Старые кадры догнаны скриптом `scripts/backfill-webp.ts`.

- **Тест, читающий ВСЮ базу, живёт в e2e, а не в юнитах (2026-08-03)**: лента админки агрегирует шесть таблиц, а юнит-файлы идут ПАРАЛЛЕЛЬНО — соседний тест успевал удалить свои записи между вставкой и чтением, и проверка падала не из-за дефекта. `retry` это лишь маскировал. Правильное место — `vitest.e2e.config.ts` с `fileParallelism: false`.

- **Мобильный Safari: `svh`, а не `vh` (2026-08-03)**: `100vh` там считается от экрана БЕЗ учёта адресной строки — первый экран вылезал под неё и дёргался при скролле. Проверка мобильной вёрстки — эмуляцией iPhone с его user-agent, а не просто узким окном: часть поведения (автоплей видео, единицы высоты) завязана именно на WebKit.

## Уроки CI/деплоя (2026-07-13, первая настройка пайплайна)
- **Лок-файл и платформенные optional deps** (sharp/emnapi/aws-sdk): `npm i <pkg>` на macOS пишет неполный lock → `npm ci` в Linux-CI падает. ПРАВИЛО: после ЛЮБОГО `npm i` сразу `rm -rf node_modules package-lock.json && npm install` (не `--package-lock-only`). Наступали 3 раза (sharp, emnapi, aws-sdk) — gate не ловит, т.к. локальные node_modules полные.
- **Тесты самодостаточны**: интеграционный тест сам создаёт нужные ему записи БД (и убирает за собой). Полагаться на «в моей базе уже есть фотограф» = зелёное локально, красное в CI.
- **Dockerfile**: `ENV NODE_ENV=production` ставить ПОСЛЕ `npm ci` и `npm run build` — иначе npm пропустит dev-зависимости (tailwind/ts), нужные билду.
- **zsh**: `$USERNAME` — зарезервированная переменная (= имя OS-пользователя), не использовать в скриптах проверок.
- **tsx-скрипты**: обязательный `import 'dotenv/config'`; инлайн `tsx -e` с `$` в bash ломается на экранировании — писать временный файл В ПРОЕКТЕ (module resolution от расположения файла).
- **Health обязан проверять зависимости**: /health без SELECT 1 дал «зелёный» деплой при мёртвом TLS к Managed PG (2026-07-13). Managed PG Яндекса требует CA-сертификат (CA.pem в образ + sslmode=verify-full&sslrootcert=…).
- **Билд проверять БЕЗ DATABASE_URL** (prepare-deploy делает `env -u DATABASE_URL`): страница со static/ISR (`revalidate`/дефолт), лезущая в БД, падает на пререндере в Docker-билде, где секретов нет. Локальный `.env` это МАСКИРУЕТ — `npm run build` проходит локально, красный в CI. Правило: страницы с запросами к БД → `export const dynamic = 'force-dynamic'` (случилось с /ru/community 2026-07-14).
- **Прод-данные — только через Actions-workflow** (инвайты, админы): локальные скрипты пишут в ЛОКАЛЬНУЮ базу; с ноутбука прод недоступен (сеть).
- **Серийная очередь деплоев медленная — не паника (2026-07-16)**: `concurrency: deploy-main, cancel-in-progress: false` → пуши деплоятся ПО ОЧЕРЕДИ; N коммитов × Docker-сборка Next.js ≈ N×4 мин (4 коммита долетели за ~16 мин). `/health` показывает только ФИНАЛЬНЫЙ образ — промежуточные SHA проскакивают. Не звать оператора «деплой завис», пока не прошло ≥20 мин застоя `/health`. CI не виден напрямую (PAT 403 на Actions/check-runs) — статус деплоя ТОЛЬКО через poll `/health` version=SHA. Приём диагностики «код или инфра»: одноразовый docker PG на свободном порту + `prisma migrate deploy && db:seed && npm test` (не трогая локальную dev-БД с реальными аккаунтами) воспроизводит CI-тест-джобу на чистой БД.
- **🔴 «Застрявший деплой» = ИСЧЕРПАНЫ МИНУТЫ ACTIONS, не код (2026-07-26, стоило часов)**: прод замер на одной версии, 8 коммитов не деплоились. Гейт+e2e зелёные, `diff prisma/` пуст, CI-репро на чистой PG зелёный — код НИ ПРИ ЧЁМ. Улика: в Actions ВСЕ воркфлоу (включая scheduled Uptime/Backup, кода не трогают) падали за **3-4 секунды ещё до шагов**. Это классический признак «private-репо выбрал free-квоту Actions (2000 мин/мес)» — GitHub не даёт джобам стартовать. Диагностика: (1) сравнить длительность ранов (успешные многомин. → потом внезапно 3-4с крах); (2) падают ли НЕ-кодовые scheduled-джобы; (3) баннер в упавшем ране «spending limit / payments failed». Фикс — оператор: поднять spending limit ($0.008/мин, ~$4 за 500мин) ИЛИ **сделать репо public** (безлимитные Actions; секреты в Lockbox/не в git → перед public скан истории+логов на утечки: `git log --all --diff-filter=A --name-only | grep -iE 'env|pem|key|cred'`, и не печатает ли fetch-secrets значения в лог). Оператор выбрал public → деплой сразу поехал. Тяжёлый CI (~10-15мин × десятки пушей) на приватном репо выбивает квоту → ВСЁ выглядит как «завис». **CI-кэш** (buildx `cache-from/to: gha` для Docker-сборки) резко удешевляет и ускоряет (деплой ~60с вместо ~4мин).
- **🔴 Деплой падает на шаге Deploy по таймауту pull образа (2026-07-31)**: CI/CD `test`+`build-push` зелёные (образ в GHCR), но `deploy` падает на «Run Command Timeout» посреди `docker pull` GHCR→VM. Причина — дефолтный `command_timeout` appleboy/ssh-action = **10 мин**, которого не хватает при медленном/зависшем pull. Диагностика: `gh run view <id> --log-failed` (gh CLI ЧИТАЕТ Actions — в отличие от PAT; но `gh run rerun` НЕЛЬЗЯ, токен без `actions:write` → перезапуск только новым коммитом). Отделить «код или инфра»: CI-репро на чистом docker-PG (`migrate deploy`+`db:seed`+`npm test`) — если зелёный и `package.json`/lock/Dockerfile/workflows не менялись, код НИ ПРИ ЧЁМ. Фикс: в `deploy.yml` ssh-action `command_timeout: 20m`. Транзиентное зависание pull лечится перезапуском; устойчивое — зеркалом реестра/предзагрузкой.
- **Сид справочников на проде**: Docker гонял только `migrate deploy` → города/категории пусты → анкета падала `city_not_found` (2026-07-14). Сид (`npm run db:seed`, идемпотентный) встроен в CMD после миграций + workflow Seed prod. Урок: любые справочные данные, нужные рантайму, засевать на старте контейнера, не только локально.

## Сетевая специфика оператора
- С ноутбука оператора провайдер режет путь к диапазонам Yandex Cloud (SSH/HTTP к VM недоступны, снаружи VM жива). Все операции с VM — ТОЛЬКО через GitHub Actions (ssh с раннеров). Проверка гипотезы при смене сети: `nc -vz <VM_IP> 22`.

- **🔴 Списки «всех файлов объекта» дублировать НЕЛЬЗЯ (2026-08-04)**: `storePhotoVariants` писал 5 объектов, а четыре независимые копии списка удаления знали про 3 — WebP не удалялся НИКОГДА. То есть отклонённый по жалобе кадр и фотографии удалённого аккаунта продолжали раздаваться именно в том формате, который предпочитает каталог. Теперь `PHOTO_VARIANTS`/`photoStorageKeys` — единственный список, три копии удалены.
- **🔴 Гейт, который нельзя пройти, = отключённая механика (2026-08-04)**: `confirmShoot` требовал подтверждённую почту, а письма не уходят → ни одной подтверждённой съёмки, ни одного verified-отзыва, пустой фильтр «с подтверждёнными». Гейт обязан спрашивать не «настроено ли», а «работает ли», и уметь сниматься рубильником.
- **🔴 Захват фоновой задачи считается ОТ МОМЕНТА ЗАХВАТА (2026-08-04)**: `requeueStuck` мерил застревание от `createdAt` (загрузки), поэтому отбирал задачу у живого воркера, если ролик пролежал в очереди дольше порога. Два ffmpeg на одну запись, гонка за ключи S3, стёртый результат. Плюс финализация теперь условная (`claimedAt`) — проигравший гонку не затирает чужой результат.
- **🔴 Отказ хранилища не должен выглядеть как «файла нет» (2026-08-04)**: S3-адаптер глотал любую ошибку → раздатчик отдавал 404, страницы рендерились с битыми картинками, smoke оставался зелёным (он как раз проверяет 404 на неизвестный ключ). Теперь `StorageUnavailableError` → 503, а `/health` пробует хранилище.
- **Дедуп не должен наказывать честного автора (2026-08-04)**: совпадение с чужим кадром в статусе PENDING блокировало загрузку — достаточно было залить чужое портфолио первым, и настоящий автор не мог собрать своё. Сравниваем только с APPROVED (и со своими).
- **В рейтинг идут ТОЛЬКО verified-отзывы (2026-08-04)**: иначе двадцать аккаунтов с оценкой «1» топят конкурента навсегда (отзывы не затухают) и невидимо для него — низкие оценки публично не показываются.

- **🔴 sharp: каскад, а не N обработок исходника (2026-08-04)**: каждый вариант декодировал ИСХОДНЫЙ буфер заново — пять проходов плюс два в анализе. На 50-мегапиксельном кадре распакованный слой — сотни мегабайт при двух гигабайтах памяти контейнера: три одновременные загрузки клали прод. Теперь исходник разбирается один раз, миниатюры и WebP строятся из веб-варианта; `sharp.concurrency(1)` — libvips иначе берёт по потоку на ядро, каждый со своими буферами.
- **Ограничения целостности — в БД, а не только в коде (2026-08-04)**: guard в приложении защищает от ошибки в одном месте, CHECK — от ошибки в любом будущем коде, в скрипте и в ручном SQL (правка базы руками в этом проекте уже случалась). Заведены на оценку отзыва и суммы платежей: там неверное значение не роняет ничего, а молча искажает публичный рейтинг и бухгалтерию.

- **🔴 Вход через чужой аккаунт по email (2026-08-04)**: регистрация не требует подтверждения адреса, поэтому аккаунт можно завести на ЧУЖУЮ почту со своим паролем — и когда настоящий владелец входит через Яндекс, он попадает в аккаунт, пароль от которого знает посторонний. Линковка теперь только с подтверждённым адресом или с аккаунтом без пароля (созданным через OAuth).
- **🔴 Условия, обещанные «навсегда», должны переживать оплату (2026-08-04)**: `prepareCheckout` брал полный прайс мимо `priceMinorLocked`, а зачисление писало `grandfathered: false` — первый же платёж стирал грант основателя и перезакреплял полную цену. Ударило бы по кругу амбассадора, то есть по самым лояльным.
- **Вес голоса — по доверию к аккаунту (2026-08-04)**: лайк свежего неподтверждённого аккаунта не двигает merit. Лайк ставится (человек видит отклик), но накрутчику нужны выдержанные и подтверждённые аккаунты, а не свежая пачка.
- **`no-unreachable` включён (2026-08-04)**: правило отключено в базовом конфиге Next, и мёртвый код после `return` спокойно прошёл гейт.

## Мутационная проверка тестов

Зелёный тест не значит, что он что-то стережёт. Проверка: внести в код мутацию, ломающую инвариант, и посмотреть, покраснеет ли батарея. Первый же прогон (2026-08-03) нашёл слепой тест на ГЛАВНЫЙ продуктовый инвариант: добавление `proRank` в сортировку каталога (то есть «подписка двигает merit-порядок») не уронило ни одного теста. Причина — тест сравнивал порядок «до и после» на профилях с ОДИНАКОВЫМ ratingScore: если подписчик и так стоял первым, подъём ничего не менял. Теперь merit задан явно и по-разному, подписку получает ВТОРОЙ, и мутация ловится. Правило: тест на «X не влияет на порядок» обязан ставить X в положение, где влияние было бы ВИДНО.

Нагрузочная база — `scripts/load-test.sh`, цифры и что они значат — vault/Проект/LOAD-BASELINE.md.

## Правило падающих тестов (a/b/c)
(a) тест устарел относительно новой правильной логики → обновить тест;
(b) регрессия → чинить код, не тест;
(c) env-зависимость → задокументировать здесь и в тесте.
«Baseline drift» как отговорка запрещён.
